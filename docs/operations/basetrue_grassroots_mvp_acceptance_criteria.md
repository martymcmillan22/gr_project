# BaseTrue Grassroots MVP Acceptance Criteria

Status: Canonical Acceptance Gate  
Updated: 2026-08-08  
Source Narrative: docs/architecture/basetrue_grassroots_mvp_snapshot.md

## Purpose

This document converts the canonical MVP snapshot into deterministic acceptance criteria.
It is the governed pass/fail contract for feature work, regression checks, and AI-assisted implementation.

## Scope

These criteria apply to all Grassroots MVP-aligned changes spanning:

1. Idea phase behavior
2. Seed phase behavior
3. Project phase behavior
4. MVP publication behavior
5. Cross-phase deterministic inheritance and orchestration

## Deterministic Gate Rules

1. Every criterion must have explicit evidence.
2. No inferred behavior is accepted as evidence.
3. Contract changes require explicit update of this file and the MVP snapshot.
4. Runtime fallback behavior is valid only when documented in this file.

## Phase Acceptance Criteria

### Idea Phase

AC-IDEA-001: Minimal entry is available

1. The phase accepts Title, Intentions, and Vision as first-class inputs.
2. No mandatory thesis structure is required at Idea entry.
3. Pass condition: user can create an Idea without Seed/Project-only fields.

AC-IDEA-002: Friction-free start is preserved

1. Idea save path does not require industry alignment fields.
2. Pass condition: Idea creation succeeds with only minimal required inputs.

### Seed Phase

AC-SEED-001: Deterministic promotion from Idea to Seed

1. Title is preserved as thesis subject context.
2. Intentions are preserved as thesis direction context.
3. Pass condition: promotion preserves values without lossy transformation.

AC-SEED-002: Seed thesis structure is captured

1. Seed thesis content covers what, why, who, and where intent.
2. Pass condition: Seed record includes thesis narrative content with deterministic persistence.

### Project Phase

AC-PROJECT-001: Economic hierarchy alignment is active

1. Project aligns to Sector, Industry Group, Industry, and Sub-Industry.
2. Pass condition: project context resolves through canonical hierarchy surfaces.

AC-PROJECT-002: Four-surface LFO contract is active

1. Math surface mode is sacp_probability_surface.
2. Language surface mode is ednp_transcript_surface.
3. Arts surface mode is vlsm_creator_surface.
4. Science surface mode is mbsp_consumer_gui_surface.
5. Pass condition: envelope includes all four surfaces with expected modes.

AC-PROJECT-003: Deterministic inheritance is present

1. 16 SEVM logical branches are generated.
2. 64 industry templates are generated.
3. 256 micro templates are generated by canonical backend flow.
4. Pass condition: inheritance chain remains append-only and deterministic.

AC-PROJECT-004: Runtime timeline governance is active

1. Timeline progression follows governed phase/slot model.
2. Phase gating is enforced through deterministic gate state.
3. Pass condition: locked phases cannot be advanced without prerequisite completion.

AC-PROJECT-005: Operational engines are available

1. Workflow orchestration is active.
2. SOP scaffolding is active.
3. Versioning and feature-management pathways are active.
4. Pass condition: project-level orchestration metadata is present and consumable.

AC-PROJECT-006: GUI endpoint path is available

1. Science (MBSP) consumer synthesis is rendered as a first-class surface.
2. Pass condition: GUI-facing synthesis metadata is available in envelope/view model.

AC-PROJECT-007: Documented micro-template fallback behavior is preserved

1. Backend micro template contract resolves 256 rows when provided.
2. Frontend fallback may resolve 64 rows when only industry templates are present.
3. Pass condition: this behavior is treated as expected fallback, not a regression.

### MVP Phase

AC-MVP-001: Investor e-book generation contract

1. MVP output includes investor-focused narrative artifact generation.
2. Artifact includes thesis, alignment, LFO structure, workflows, SOP, business context, and roadmap sections.
3. Pass condition: deterministic investor artifact build completes from project state.

AC-MVP-002: Product usage e-book generation contract

1. MVP output includes user-facing usage artifact generation.
2. Artifact includes product behavior, workflow usage, SOP usage, update model, GUI behavior, onboarding, and scale sections.
3. Pass condition: deterministic product-usage artifact build completes from project state.

AC-MVP-003: Dual identity output

1. MVP must produce both external (investor) and internal (usage) identities.
2. Pass condition: both artifacts are generated from deterministic state without ad hoc content dependencies.

## Cross-Phase Invariants

AC-INV-001: Deterministic continuity

1. Phase promotion does not break naming continuity across layers.
2. Pass condition: identifiers remain stable from capture through runtime envelopes.

AC-INV-002: Unified intelligence envelope continuity

1. Timeline, semantic state, orchestration, and surface contracts remain bindable into one intelligence state.
2. Pass condition: downstream consumers can derive coherent view models without ambiguity.

AC-INV-003: No silent contract drift

1. Surface modes, template counts, and phase-gate semantics must not change silently.
2. Pass condition: any intentional contract change includes matching test and docs updates.

## Evidence Requirements

A change passes only when all relevant evidence is attached:

1. Automated test output for impacted backend and frontend slices.
2. Contract-shape assertions for envelopes and view models.
3. Documentation updates for any intentional behavior change.

## Definition of Done for MVP-Aligned Changes

A change is accepted only if:

1. All applicable AC IDs above are satisfied.
2. Deterministic invariants remain intact.
3. Evidence is attached and reproducible.
4. Runtime fallback behavior remains consistent with AC-PROJECT-007.
